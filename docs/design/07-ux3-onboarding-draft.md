## 0. 一屏摘要

```markdown
- 问题：新手「建房优先、不知建商业」，Lv2→Lv3 徘徊 169~220 tick（熟练 57~64），两位新手独立复现
- 机理：Lv2 解锁食肆（5 分、运转才计分）是此段唯一增量来源；空茅舍按入住率折算≈0 分、原料建筑封顶 26
- 方案：3 条检查点式提示（T1 商业缺失 / T2 空屋过度 / T0 开局引导），非模态提示条，每局每条至多一次
- 边界：纯 UI 层 + 只读谓词；RULES 零改动；bot 与验收探针不受影响
- 验收：2 位不同新玩家 × 各自首局，徘徊段 ≤100 tick；115+33 全绿 + 新增单测
```

## 1. 问题机理（为什么新手会卡住）

Lv2→Lv3（繁荣度 20→60）阶段，玩家可用的繁荣度来源：

| 来源 | 分值 | 新手可感知性 |
|---|---|---|
| 茅舍（空屋） | 1 × 入住率 ≈ 0 | ❌ 盖了 13 间却几乎不涨分（P3-G2 实测）——**反直觉**，是弯路的核心 |
| 农田/林场/粮仓 | 恒计分，合计封顶 26 | ⚠ 铺到顶也到不了 60 |
| **食肆（Lv2 解锁）** | **5 分，运转才计** | ❌ 不知道它是产钱的、不知道要配食物链（农田→磨坊→食） |
| 磨坊 | 4 分，运转才计 | ⚠ 同理 |

现有引导的缺口（实测证伪）：升级 toast 已播报「解锁【食肆、粮仓】」、繁荣度条下常驻「断链/闲置建筑不计繁荣度」——**两者都只陈述规则，不给行动指向**，P2/P3 全部看过、全部没拦住。

## 2. 方案：检查点式提示（3 条）

**呈现形态**：HUD 下方新增非模态提示条（hint bar）——不锁操作、不遮挡画布、不暂停游戏；带 ✕ 可手动关闭；条件消失时自动消失；**同一提示每局至多出现一次**（关闭或消解后不复发）。同屏至多一条，优先级 T1 > T2 > T0。

### T1 商业缺失提示（主提示，对症核心弯路）

- **触发**：`level ≥ 2` 且 **食肆数 = 0** 且 **繁荣度停滞**（ trailing 60 tick 内 Δprosperity < 1.0 ）
- **文案**：「食肆已解锁——它把食换成铜钱，**运转中的商业才计繁荣度**。食从哪来？农田 → 磨坊。」
- **消解**：建成食肆（条件不满足即自动消失）
- 设计说明：60 tick 停滞窗口的取值对标熟练玩家徘徊段 57~64 tick。**熟练玩家不会触发**的机理（C-3 修正）：其徘徊段内繁荣度持续在动（60 tick 内 Δprosperity 远超 1.0 阈值），停滞条件不成立——与窗口长度无关，窗口取值仅用于框定「真卡住」的判定时长。只有真正卡住的新手会看到。

### T2 空屋过度提示（对症「建房优先」签名）

- **触发**：**空置民居容量 ≥ 6**（ housingCapacity − population ≥ 6 ，约 3 间空茅舍当量）且 `level ≥ 2` 且繁荣度停滞（同 T1 口径）
- **文案**：「空屋不住人——民居繁荣度按入住率折算。当前户数 {N}/容量 {M}，先让人住满再盖新房。」（**带入实时数字**，把不可见的折算公式变成可读事实）
- **消解**：空置容量 < 6

### T0 开局引导（D-U2 已拍板纳入，针对 P3-G1 开局静默 30+ tick）

- **触发**：`tick ≥ 20` 且建筑数 = 0
- **文案**：「从农田和林场开始——粮与木是一切的源头。」
- 说明：低风险低成本，但「观察 30 tick」也可能是玩家自主行为，提示价值待验证——**D-U2 已拍板纳入本期（2026-10-18 14:54，R5 风险评级「中」知悉）**。
- 文案边界注记（C-5，门控评审补充）：本条是三条中唯一带「行动指向」的文案，与「明确不做：不提示建造顺序」存在张力。辩护依据：Lv1 可建建筑中 farm/forest 是全部产出的唯二源头（机制因果），且 T0 只在零建筑时触发一次。D-U3 拍板时已按此边界审视通过。

### 明确不做

- 不做强制引导/锁定操作；不做高亮箭头遮罩；不做多步教学流程；
- 不碰 `RULES`、阈值、公式、造价、速率（冻结令）；
- 不提示「最优建造顺序」——只讲机制因果（什么计分、钱从哪来），把决策留给玩家。

## 3. 技术方案（落实现有分层纪律）

| # | 任务 | 内容 | 层 |
|---|---|---|---|
| T-UX3-01 | `src/config/uiHints.js` | 触发参数独立配置（停滞窗口 60 / 停滞阈值 1.0 / 空置阈值 6 / T0 时刻 20）——**不进 RULES**，冻结令不受触碰 | config |
| T-UX3-02 | `src/core/hints.js` | 纯函数 `evaluateHints(state, history)` → 当前应激活的提示 id 列表；零 DOM、零 state 写入（与 telemetry 同纪律：只读观察者） | core |
| T-UX3-03 | `src/ui/hintBar.js` + style.css | 提示条组件：show/hide/dismiss，琥珀色样式，每局每 id 一次性 | ui |
| T-UX3-04 | main.js 装配 | afterTick 内维护繁荣度环形缓冲（60 tick）、调用 evaluateHints、驱动 hintBar；提示事件写入遥测 | 装配层 |
| T-UX3-05 | telemetry.js 增 `hints` 字段 | `hints: [{tick, id, action: shown/dismissed/resolved}]`——**additive 超集字段**，沿用 samples 超集先例，不改既有 schema 语义 | core |
| T-UX3-06 | `tests/hints.test.js` | 单测：触发条件、停滞窗口判定、优先级、一次性、消解 | tests |

**影响的既有文件**：仅 `main.js`（装配）与 `telemetry.js`（additive 字段）。**`simulation.js` / `rules.js` / `buildings.js` / 全部既有测试零改动。**

**工程注记（C-6，门控评审补充）**：① hints 提示状态若随遥测持久化，serialize/restore 须容忍旧档缺失该字段（scarcity 先例，保证 v1.3 旧档可恢复）；② 「首个食肆 tick」从 samples（30 tick 粒度）近似读出，跟随时延测量误差 ±30 tick——对 A4 的量级判断（≤100 vs 基线 169~220）足够，不要求精确到 tick。
