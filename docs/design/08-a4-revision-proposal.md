## 1. 前提：A4 到底败在哪

两类新手、两种病灶，**单一触发口径 + 单点文案无法同时覆盖**（A4 报告 §3/§4）：

| 分型 | 样本 | 徘徊段 | 病灶 | 提示有效吗 |
|---|---|---|---|---|
| **P4 缓慢爬升型** | 1 人 | **281** tick | 停滞口径抓不到慢爬：繁荣度 24→40 以 6~8 分/60tick 爬升，60 tick Δ 恒 ≥1.0，**永不判停滞**，直到 tick 210 进平台期才在 245 触发（已徘徊 209 tick，占 74%） | **有效但太晚**：resolved@289 → Lv3@317，仅 **28 tick**。玩家备注「食肆解锁后速度加快」互证 |
| **P5 停滞型** | 1 人 | **358** tick | 触发合格（@145），但 **107 tick 才响应**，响应后集中超建 10 座食肆 → food=0、繁荣度 49→36.5 回落，resolved 后又花 **137 tick** | **触达但没懂**：知道要建食肆，不知道食肆要食链支撑 |

**这两条证据的方向是相反的**，所以不能用同一个改动救两个人：P4 缺的是「更早」，P5 缺的是「更深」。这决定了 a 和 b 是两个正交改动，不是二选一。

## 2. 代价评估口径

每条按七项打分：**改动面**（文件/行数）· **冻结令**（是否触碰 RULES）· **误伤风险** · **可验证性**（能否用现成数据先验）· **工期** · **样本充分性** · **失败后果**。

> 说明：本文的"天"按单个 agent 串行执行 + 含验证计，与 06 文档「humanRound3Bot 复放约半天」同一口径。

## 3. 四条逐条评估

### a) T1 文案补「恒计分 vs 运转计分」区分

| 项 | 评估 |
|---|---|
| 对症 | P5 第 2 层卡点（「没有粮，也能提升繁荣度。不懂这个游戏的机制」） |
| 改动面 | `src/core/hints.js::hintText('t1')` 字符串 + `docs/design/07` §2 文案表。**代码约 5 行** |
| 冻结令 | **零触碰**（纯文案，不涉 `rules.js`/`buildings.js`） |
| 误伤风险 | 低。但有一个真实副作用：**横幅长度**。现文案 34 字，补区分说明后约 50~60 字，`style.css` 是 HUD 下方单行横幅，需检查换行/遮挡；建议控制在 2 行内 |
| 可验证性 | **弱**。文案理解度只能靠访谈，无硬指标。可加代理观测量：「提示后 60 tick 内是否建食肆」（hints 事件级已能读） |
| 工期 | **0.5 天** |
| 样本充分性 | 1 个（P5）。但这是"补漏"不是"设计"，样本要求可放宽 |
| 失败后果 | 低——文案错了玩家最多读一句废话，不会把游戏玩坏 |
| 现有单测 | `tests/hints.test.js:174` 只断言 `toContain('食肆')`，**改文案不会红** |

**结论：建议做，但必须与 b 同批**。单独做的唯一效果是让 P5 型从"照做后管崩"变成"可能不那么崩"，**A4 主判据仍然 FAIL**。

### b) T1 触发口径：停滞 → 停滞 **OR** 增速不足

| 项 | 评估 |
|---|---|
| 对症 | **P4 的根因**，且是四条里唯一针对"结构性盲区"的改动 |
| 改动面 | `uiHints.js` +2 参数；`hints.js` +1 谓词 `isSlowGrowth()` + `t1Condition` 改 OR；`main.js:304` 缓冲裁剪改 `Math.max(...)`。**约 30~50 行（含 4~6 条单测）** |
| 冻结令 | **零触碰**，理由见 §5 |
| 误伤风险 | **中低**，有结构性护城河：`t1Condition` 的前置条件是 `level≥2 && eateryCount===0`，熟练玩家在 Lv2 后约 30 tick 内即建食肆（R1 两局 `hints:[]` 的成因），**在阈值窗口填满（61 tick）之前就已不满足条件**，天然免疫 |
| 可验证性 | **强**。13 局遥测里含 P4/P5/R1×2 的逐 tick 曲线，可先做**离线回放**判定"该触发谁、不该触发谁"，不必等真人 |
| 工期 | **1.5 天**（标定 0.5 + 实现 0.5 + 13 局回放 0.5） |
| 样本充分性 | 2 个（P4 慢爬型 1 + 熟练对照 2），标定所需的**分离区间极宽**（见 §6），样本够用 |
| 失败后果 | 阈值定错有两侧风险：过低→误伤熟练玩家（UX 从"没帮上"变"烦人"，而这正是 R1 要防的）；过高→等于没改（P4 仍然 245 才触发） |

**结论：★必做，且排第一。** 它是唯一能改变 P4 结局的改动，P4 占失败样本的 1/2，且失败幅度最大（281 tick，是线的 2.8 倍）。

### c) 阶段目标式引导（回应「无聊 / 不知道该干嘛」）

| 项 | 评估 |
|---|---|
| 对症 | P5 第 3 层卡点（目标感缺失），属**引导体系结构性缺口** |
| 改动面 | UI 新组件 + 目标状态机 + 遥测新字段 + 协议升版 + 判定带。**3~5 天，且是唯一需要动协议的一件** |
| 冻结令 | 不碰数值，但会占 HUD 空间（T1/T2 横幅已占 HUD 下方，需重排布局） |
| 误伤风险 | 中。目标式提示若做重（如"当前目标：繁荣度 60"常驻）会变成压力源，与"拉节奏不施压"的 UX 定位冲突 |
| 可验证性 | **弱**。目标感是主观体验，只能靠 paceVerdict + 访谈，n=1 时无法判定 |
| 工期 | **评估 0.5 天 / 实施 3~5 天** |
| 样本充分性 | **1 个（P5 一人一句备注），且与"机制不懂"混杂**——同一局里两层卡点叠加，无法归因目标感单独贡献多少 |

## 4. 推荐方案：一次改完，不拆两轮

| 阶段 | 内容 | 工期 | 产出 |
|---|---|---|---|
| 1 | **a + b 同批实施**（同一 commit，都在 `uiHints.js`/`hints.js`） | 1.5~2 天 | 代码 + 单测 + 07 文档 §2/§3 同步 |
| 2 | **13 局遥测离线回放**：验证"P4/P5 会触发、R1 两局仍零触发、其余 9 局误触发率" | 含在第 1 阶段 | 回放报告（判定口径先于真人） |
| 3 | **d 真人复测**：2 位新玩家 × 首局 | 1 天 | A4 判定报告 + 协议同步 |
| 4 | **c 评估**（并行，不阻塞 1~3） | 0.5 天 | 一页评估，等阶段 3 数据再定 |

**为什么不拆成"先 a 复测、再 b 复测"**：复测要拉 2 位新玩家，单轮成本 1 天。拆两轮 = 多 1 天 + 多 2 位玩家配额，而区分 a/b 各自贡献并不需要分组——**hints 事件级数据（触发 tick / 跟随时延 / 触发后行为序列）本身就能归因**：若复测中触发 tick 显著前移（从 245 → ~100），那是 b 的贡献；若触发后建成时延缩短、断链减少，那是 a 的贡献。

## 5. b 的三个技术陷阱（实施前必读）

**① T2 与 T1 共用 `isStagnant`，不能直接改 `stagnationDelta`。**
`hints.js` 里 `t1Condition` 和 `t2Condition` 都调 `isStagnant()`。若把 `UI_HINTS.stagnationDelta` 从 `1.0` 调到 `12`，T2（空屋过度）也会变成"增速不足即触发"——而 T2 的前置只有"空置容量 ≥6"，**没有"无食肆"这道护城河**，会在新手正常建房期频繁误弹。
→ 正确做法：**新增独立参数** `growthWindow` / `growthDelta`，只在 `t1Condition` 里以 OR 叠加，`t2Condition` 保持纯停滞。

**② `main.js:304` 的缓冲裁剪是硬编码 `stagnationWindow + 1`。**
`if (prosperityHistory.length > UI_HINTS.stagnationWindow + 1) prosperityHistory.shift();`
若 `growthWindow > stagnationWindow`，历史被裁短 → 增速判定永远采样不足 → **静默永不触发**（最危险的失效形态：不报错、不触发、看起来"改动生效了但没效果"）。
→ 必须改为 `Math.max(UI_HINTS.stagnationWindow, UI_HINTS.growthWindow) + 1`。**并且这条要有专门的单测**：断言缓冲长度 ≥ 两个窗口的最大值 +1。

**③ 现有单测 `tests/hints.test.js:98-101` 的语义会被 b 反转。**
该用例构造"繁荣度每 tick +0.2（即 12 分/60tick）"，断言 **`isStagnant=false` 且 `evaluateHints` 为空**——它编码的正是旧设计意图「慢爬不算卡住」。b 落地后这个输入**恰好落在增速不足区间**（12/60tick 正是 P4 量级），T1 应当触发。
→ 不是删掉它，而是**改写语义**：保留 `isStagnant=false` 断言（停滞口径没变），另加一条断言「但 `isSlowGrowth=true` → T1 触发」。删掉它就等于把这个设计转折点从测试里抹掉了。

## 6. 参数标定：为什么 b 的风险是可接受的

关键在于**分离区间足够宽**，标定不敏感：

| 群体 | 繁荣度增速（每 60 tick） | 来源 |
|---|---|---|
| P5 停滞型 | **0**（tick 90~240 冻结在 29） | A4 报告 §3.2 |
| P4 缓慢爬升型 | **≤8**（60→120 段 +6、120→180 段 +8、150→210 段 +4） | A4 报告 §3.1 |
| 熟练玩家（R1） | **≥19~20** | ㉚ / `ux3-r1-evidence` |

**分隔空档：8 → 19，约 2.4 倍**。建议初值 `growthDelta = 12 / 60tick`（0.2/tick），两侧各留 1.5~1.6 倍余量。

**推算效果（未实测，仅作排序依据）**：若阈值 12，P4 在缓冲填满（Lv2@36 + 61 = tick 97）时 Δ≈+3 → 即刻触发，比现状（tick 245）**提前 148 tick**；按其已验证的 28 tick 响应时延，Lv3 约在 125 达成，徘徊段 **≈89 tick，可过 ≤100 线**。这也是把 b 排第一的量化理由。

⚠ **标定必须用 R1 两局的逐 tick 曲线回放，不能只看报告摘要里的「Δ≥19~20」**——摘要值是徘徊段平均，局部 60 tick 窗口可能更低（尤其是 Lv2 刚达成、恒计分建筑尚未铺开的窗口）。回放时逐窗口求最小 Δ，才能确认 12 是否安全。

## 7. 验收口径（沿用现行，不新增）

- **主判据**：2 位不同新玩家 × 各自首局，Lv2→Lv3 徘徊段 ≤100 tick（**A4 判据不动**，281/358 vs 100 的差距非判据过严）
- **子判据 1**：`hints` 事件级可读出「提示 tick → 首个食肆 tick」跟随时延（已达标，保持）
- **子判据 2（新增，防误伤）**：R1 两局回放仍为 `hints: []` 零触发
- **子判据 3（新增，防过期提示）**：单局提示数 ≤3、`oncePerRun` 无复发（A5，本轮已获首个正样本 n=2）
- **协议**：若 c 实施才需升 v1.6；a/b 不涉协议字段，**无需升版**

## 8. 明确不做

- ❌ **不动参数微调**（缩短 `stagnationWindow` / 调小 `stagnationDelta`）：A4 报告 §6.3 已证伪，对 P5 型无效、对 P4 型只是提前触发而非解决。
- ❌ **不动 A4 判据本身**。
- ❌ **不为两类新手做两套文案**：b 只改时机不改内容，v1 保持单一 T1 文案（拆两套会让 `evaluateHints` 需要分型状态，成本翻倍且分型判据本身未钉）。
- ❌ **不在 b 里顺手补 P5 的"照做后管崩"缺口**（食肆已建但断粮时无提示）：这是独立覆盖漏洞，属 a/c 的领域，别混进 b。
