## 5. 存档兼容性

| 问题 | 结论 |
|---|---|
| `saveVersion` 是否 bump？ | **不建议 bump（保持 1）**。理由：① 序列化字段集完全没变（`serialize` 的 11 个字段一个没动）；② `maxLevel` 在 P3 已经入档并有「旧存档无该字段 → 用 `data.level` 兜底」的兼容分支（`src/core/save.js:33`）；③ bump 的代价是**所有旧存档直接作废**（`loadGame` 版本不符返回 null），而本轮改动不产生任何需要丢弃的结构性变化 |
| 旧存档载入后等级怎么表现？ | `deserialize` 原样恢复 `prosperity` / `level` / `maxLevel`，**第一个 tick 就按新阈值重算** `computeLevel`。例：旧存档繁荣 120、`level=4`、`maxLevel=4` ⇒ 新版瞬时 `level` 变 **3**（60 ≤ 120 < 150），但 `maxLevel` 保持 **4** |

## 6. 遥测与协议同步（**必须随 P-1 一起做，否则数据静默作废**）

`src/core/telemetry.js:15` 把里程碑阈值**硬编码**为 `{ lv2: 20, lv3: 50, lv4: 100 }`（注释写"与 `rules.unlockThresholds` 同源"——同源但不同步）。P-1 抬阈值到 60/150 后：

- `milestones.lv3` 会在繁荣度 **50** 时打点（真实 Lv3 是 60）⇒ M2 数据偏早；
- `milestones.lv4` 会在繁荣度 **100** 时打点，`finalSnapshot` 也在那一瞬拍（真实通关在 150）⇒ **M3/M6 数据直接错**；
- 而面板自动弹出是按 `state.maxLevel >= 4` 触发的（`src/main.js:282`），**不会跟着错弹** ⇒ 这个错误完全静默：玩家看到面板在正确时机弹出，导出的 JSON 里 `milestones.lv4` 却是另一个时刻的数。

**建议修法（唯一真源）**：

```js
import { RULES } from '../config/rules.js';
// 里程碑阈值从 unlockThresholds 派生：调阈值时遥测口径自动跟随，杜绝"同源不同步"
const MILESTONE_THRESHOLDS = {
  lv2: RULES.unlockThresholds[1],
```

## 8. 额外风险（team-lead 清单之外，我在这轮分析里发现的）

### 8.1（P0，最高优先级）P-1 与不可修改的验收基准硬冲突 —— 见 §0

补充几点判断依据，供拍板：
- 「只抬阈值不削恒计分」（V2）虽然能通关，但**最高繁荣度 150.24 对阈值 150，余量只有 0.24 分**。任何微小扰动（bot 建造顺序、闲置波动、浮点）都能把它翻红。这种"贴着线过"的基准极其脆弱，不建议作为交付状态。
- 「只削恒计分」（V1）主用例 567 ✓，但**注入铜钱的对照用例红**。这条用例的语义是"解除铜钱约束后链路走得通"，削恒计分后它的上限只剩 86.56 —— 说明这个 bot 在"钱不是问题"时反而被**劳力**卡死（户数只有 12，劳力不够，磨坊/食肆/木匠铺大量闲置 ⇒ idle=0 不计分）。**恒计分被削掉后，bot 的分数几乎全部依赖劳力，而 bot 自己不会为劳力去扩产**——这是削恒计分对"笨 bot"的结构性副作用，真人玩家（会主动补磨坊+民居）未必受影响，但验收基准会。
- **备选 P-2（G2）对验收基准友好得多**：它不动阈值（20/50/100）、不动迁入，只削恒计分 + 改通关条件为"繁荣 ≥100 维持 400 tick"。但它需要新增 UI，且它同样会踩到 V1 那条"注入铜钱用例上限 86.56 < 100"——**G2 也需要重新审视这个边界**（86.56 < 100 ⇒ 该用例同样会红）。这点请转给文策渊复核。

### 8.2（P0 机理）bot 的 Lv3 阶段繁荣度存在**结构性上限**，不是时间问题

推导（bot 的 `wants` 自建上限）：农田 ≤6、林场 ≤12、磨坊 ≤6、粮仓 ≤1、木匠铺 ≤6、食肆 ≤6，杂货摊锁在 Lv4 ⇒
- **score=2（现网）**：非民居上限 = 12+24+24+2+24+30 = **116**，加住房分 `min(茅舍数+3×瓦屋数, 户数/2)`（H8 天花板），户数峰值 ~75 ⇒ 上限 ≈ **153**（实测 150.24 ✓ 吻合）
- **score=1（P-1）**：非民居上限 = 6+12+24+2+24+30 = **98**，加住房分 ≤ 户数/2 ⇒ **上限 ≈ 98 + 户数/2**（实测 128.33 @户数 65 ✓ 吻合）

⇒ **杂货摊（6 分 × 至多 8 座 = 48 分）被锁在 Lv4 之内，而 Lv4 又要 150 分 ⇒ 鸡生蛋死锁：不解锁杂货摊就到不了 150，到不了 150 就解锁不了杂货摊。** 这是"卡死"的真正原因，也是为什么 6000 tick 也救不回来。

**顺带证伪一个可能的"补救办法"**：我试过把杂货摊解锁等级从 Lv4 下调到 Lv3（不动阈值 150）——**仍然红**（moveIn5 上限 128.33、moveIn8 上限 112.24 都没变）。因为 bot 在 Lv3 阶段**根本不缺建筑名额**：它卡的是户数（H8 天花板 98 + 21/2 ≈ 108），不是建筑种类。所以"提前解锁杂货摊"救不了这个 bot。

### 8.3（P1）H8 天花板 —— team-lead 已点名，这里给出 P-1 下的定量后果

住房分 = `min(民居基础分合计, 户数/2)`。P-1 下 bot 稳态户数只有 **21~23**（不是设计推演里的 69），⇒ 住房分天花板只有 **~11 分**。原因链：户数 ← 迁入速率 ← 食产能 ← 磨坊数（bot 自建上限 6 座 = 6 食/tick ⇒ 理论支撑 60 户，但**任何一次闲置都会让食转负 → 迁出螺旋**，实测 t500 后从 61 户崩到 21 户并在 21~23 长期震荡）。
**结论**：在 P-1 下，bot 既拿不到户数（劳力不足 → 建筑闲置 → idle=0），也拿不到住房分（户数天花板）。**抬阈值到 150 要求的"户数 64~81"是这个 bot 达不到的**——设计侧 `F2` 推演的终局户数是 69，那是**爬山搜索出的优化策略**，不是验收 bot。两个口径差了 3 倍户数。**这条必须在设计侧对齐：要么设计用"验收 bot 策略"重跑 L\***，要么承认 L\* 与验收基准是两套标准、并明确以哪套为准。

### 8.4（P1）`moveInInterval` 5→8 的额外影响（team-lead 要求单独列出）

除"首户从 tick 5 推到 8"外，实测额外影响：
1. **bot 的 Lv3 阶段可达上限从 128.33 降到 112.24（−16 分）** —— 因为户数更少（22 vs 21 稳态、峰值更低），H8 天花板更低。这是它对验收基准最实质的影响，比"首户晚 3 tick"重要得多。
2. 开发自测红 1 条（`simulation.test.js:139`）。
3. 主用例通关 tick 515 → 600（**+17%**，比设计侧推演的 +6% 高一倍多——设计侧那个 +6% 是在 L\* 口径下测的，验收 bot 口径下是 +17%）。
4. 与阈值存在**耦合**：阈值边界 128（moveIn5）→ 112（moveIn8）。**两项不能各自取边界值**（见 Step 4）。
5. 对 §7.1 不变量表第 3 行（"钱 0 户 0 有可拆建筑 → 拆磨坊建茅舍 → 首户"）的影响：首户 tick 5→8，仍有限步，设计侧已记录，**工程侧无需额外处理**。

### 8.5（P2）数值改动在开发自测里"无声"

见 §2.5：改 farm/forest 分值开发自测 0 红。今天 B3 的教训是"看起来合法的假值比明显的错误值更危险"，这条是同构的"**无声的数值改动比报错更危险**"。建议补配置基线快照测试。

### 8.6（P2）旧存档等级回落会触发 HUD 文案自相矛盾

见 §5。P-1 会把这个既有边缘情况变成"每次载入旧存档必现"。

### 8.7（P3）本轮试玩数据与下一轮不可直接比较

即便 P-1 拍板实施，`production/playtests/` 里那 4 局是**旧阈值 + 旧公式**下的数据。加上 B3 修复后 `gameBuild` 现在带 `-dirty` 标记，下一轮导出的 JSON 能用 `gameBuild` 精确区分版本了，但**跨版本的节奏对比必须在报告里显式标注"阈值口径不同"**，否则会重演"用新旧公式逐帧拟合反证"的高成本归因。

### 8.8 与 quality-lead 独立复核的对账（2026-10-17，结论无冲突，仅口径不同）

quality-lead 用 `scratch/verify-threshold-boundary.mjs`（同样逐字搬运验收 bot、基线 12/315/515 校准）独立扫出边界后报了两组数字。我把它与我的口径放进**同一个 harness** 复跑（`D:/tmp/p1probe/probe3.mjs`），结果如下——**两边数字都对，差异来自"抬阈值"和"削恒计分"各自有两种定义**：

| 口径 | Lv3 阈值 | 恒计分处理 | 迁入 | 实测边界 | 来源 |
|---|---|---|---|---|---|
| A | **50（不动）** | 无 | 5 | **≤140**（150 未到达，上限 145.9） | quality-lead scan A；我复跑一致 ✓ |
| B | **60（同抬）** | 无 | 5 | **≤150**（160 未到达，上限 150.2） | 我的 V2 口径 |
| C | 60 | **score 2→1（P-1 原文）** | 5 | **≤128**（129 未到达，上限 128.3） | 我 |
| C8 | 60 | score 2→1 | **8** | **≤112**（115 未到达，上限 112.2） | 我 |
| D | 60 | **恒计分封顶 24（P-1′）** | 8 | **≤约 120~129**（120 ✓ / 130 ✗，上限 120.3） | quality-lead P-1′；我复跑一致 ✓ |

**跨口径共同成立的硬事实（可直接引用）**：
1. **Lv4 = 150 在 A / C / C8 / D 四种口径下全部越界**（只有 B 口径勉强过，且余量仅 0.24 分）。
2. **「注入 100000 铜钱」对照用例在 Lv4=150 下，五种口径全部 FAIL**（上限 132.3 / 134.3 / 85.8 / 81.2 / 85.8）⇒ **与钱无关**，是 bot 自身建筑配额 + 户数天花板（H8）的问题。这条把 quality-lead 在 D 口径下的观察推广到了全部口径。
3. **永久卡死复现互证**：P-1（C）与 P-1′（D）在 150 下跑到 **8000 tick 仍未到达**（上限 128.3 / 120.3），与我 6000 tick 的结论一致。
4. **边界是断崖不是斜坡**：C 口径下 128 ✓（Lv4@600，户数 65）与 129 ✗（永久冻结在 21 户）只差 1 分。机理：户数崩塌发生在 t≈750 前后，**没能在崩塌前跨过阈值就再也回不去**。⇒ 任何"卡在边界附近"的阈值都极危险，必须留足余量。

**一个反直觉的耦合效应（调参须知）**：只抬 Lv4（Lv3 保持 50）时 bot 上限 145.9 到不了 150；**把 Lv3 也抬到 60 反而能过 150**（@623）。原因是 Lv3 门槛抬高改变了 bot 的建造顺序（木匠铺/瓦屋解锁延后），终局户数从 23 变成 75。⇒ **调一个档位的阈值会通过"解锁时机→建造顺序→户数"链路影响另一个档位的可达性，不能孤立地评估单档阈值。**

### 8.9 R-bot1 / R-bot2 修复原型实测（2026-10-17，未落地，仅供决策）

design-strategist 给出 bot 修复规格（R-bot1 去硬配额 / R-bot2 食流自救 / R-bot3 先复现基线）后，我在探针里**先做了原型再谈授权**（`D:/tmp/p1probe/probe4.mjs`，仓库外、未改任何文件）。四种 bot 版本 × 四种配置：

| 配置 | legacy（现行） | 仅 R-bot2 | 仅 R-bot1 | R-bot1+R-bot2 |
|---|---|---|---|---|
| 现网基线 V2 | 12/315/**515** | 12/315/603 | 12/280/480 | 12/280/**480** |
| 现网 V1（注入铜钱） | 91 | — | — | **106** |
| P-1（score1，60/150，迁入8）V2 | ❌ 112.2 | ❌ 120.8 | ✅ 720 | ✅ **720** |
| P-1 V1 | ❌ 81.2 | — | — | ✅ **385** |
| P-1′（封顶24，60/150，迁入8）V2 | ❌ 120.3 | ❌ 126.8 | ✅ 693 | ✅ **693** |
| P-1′ V1 | ❌ 85.8 | — | — | ❌ **144.2**（差 5.8 分） |
| 保底（封顶24，阈值不动）V2 | ✅ 530 | 624 | 511 | ✅ **511** |
| 保底 V1 | ✅ 101（余量 1.08） | — | — | ✅ **141** |

**结论（可直接用于决策）**
1. **R-bot1 是救活的关键，R-bot2 单独救不了**：只加自救，P-1 从 112.2 → 120.8（仍差 29 分）、P-1′ 120.3 → 126.8（仍差 23 分）。但 R-bot2 单独能把终局户数从 22 拉回 56 ⇒ **design 的"食流被自己的配额顶死"诊断完全正确**，只是"光有人口还不够，还得有分数来源"。
2. **R-bot1 生效后 R-bot2 变冗余**：`nocap` 与 `both` 结果逐 tick 相同（720 / 693）。建议 R-bot1 必做、R-bot2 作为防御性规则保留（不增加风险，对"钱多地少"等边界更稳），优先级可降。
3. **基线漂移比预期小**：515 → 480（**−6.8%**），V1 91 → 106。不是"大幅下降"。
4. ⚠ **修 bot 之后 P-1 与 P-1′ 不再等价**：P-1 双 Gate 全绿（V2@720 / V1@385）；**P-1′ 的 V1 用例仍红**（144.2 < 150）。⇒ 即使修 bot，**P-1′ 仍需把 Lv4 降到 ≤140**（实测 140 ✅@337、150 ❌）才能双绿；而 **P-1 在 150 下就能双绿**。
5. **保底方案（封顶24 + 阈值不动）在两种 bot 下都双绿**（legacy 530/101、修后 511/141），是最稳的一条路；但 legacy 下 V1 余量仅 1.08 分。
6. 交叉印证：我的 R-bot1 原型在 P-1′ 下 693，与 design 无上限策略的 678 差 **2.2%** ✓。

**工程侧补充（design 规格里没覆盖的）**
- **「恒计分封顶 24」不是配置改动，是公式改动**：`src/core/simulation.js` 的 `computeProsperity` 现在没有封顶逻辑，需新增 `Math.min(passive, cap)`，并在 `RULES` 里加字段（如 `prosperityPassiveCap: { buildings: ['farm','forest','granary'], max: 24 }`）作为**单一真源**——绝不能把 24 硬编码进公式，否则就是第二个 D1。
- 影响面：prosperity → level → HUD 进度条 / 解锁提示 / toast / 存档重算；需新增单测；存档兼容靠 `maxLevel` 粘性兜底（已解锁内容不回收）。
- 封顶值必须进 D10 配置快照测试。

**红线提示**：修 bot = 修改 `tests/verification/progression.test.js`，与"严禁修改独立验收"纪律**直接冲突**。我未获明确授权前不动它；若授权，必须走基准升版流程（旧基线 12/315/515 + V1 91 归档留痕，新基线 12/280/480 + V1 106 写入 `HANDOVER.md` §5 与 `docs/design/02-pacing-tuning.md` §3.1，注明变更原因与日期）。另注意：修 bot 后 bot 变快（480 < 515）⇒ **真人/bot 倍差 k 需重算**，design 的 k=1.4/2.0 是在旧基线上标定的。
