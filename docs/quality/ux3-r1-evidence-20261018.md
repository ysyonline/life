## 4. gameBuild 指纹失真专项 —— 推断成立，Major，本轮可补救

### 4.1 现象

两份 JSON 的 `gameBuild = "5f77ecc-dirty"`（`gameBuildDirty: true`），但：

- `5f77ecc` =「第 3 轮试玩判定」docs commit（2026-10-18 09:15:37）；
- UX-3 实施 commit `cb4d22d` 提交于 **2026-10-18 16:14:16**，早于两份导出时刻（16:17:44 / 16:22:43）；
- 两局 JSON 顶层均存在 `hints` 字段——该字段由 `cb4d22d` 对 `src/core/telemetry.js` 的新增改动引入（`git show cb4d22d -- src/core/telemetry.js` 可证），**5f77ecc 时代不存在**。

### 4.2 推断核实 —— 成立

**推断链**：

1. `hints` 字段的存在性（且为合法空数组而非 undefined/缺失）是**确定性反证**：`getTelemetryData()` 输出 `hints` 字段的分支只有 `cb4d22d` 的 telemetry.js 才包含。字段存在 ⇒ 玩家跑的运行时代码**确含 UX-3**。
2. 但 `gameBuild` 却指向更早的 `5f77ecc`——二者矛盾，说明 `gameBuild` 指纹与运行时模块代码**版本不同步**。
3. 机理（`vite.config.js` + 协议 §4.2 明文）：`resolveBuildFingerprint()` 在 **dev server 启动那一刻**执行 `git rev-parse --short HEAD` + `git status --porcelain` 并 `define` 注入。协议 §4.2 已预警：**「dirty 状态在 npm run dev 时是启动那一刻的快照，dev 期间新改动不会自动更新（需重启 dev server）」**。
4. 结论：dev server 自 `5f77ecc`（启动时 HEAD）起**长运行未重启**，期间 UX-3 代码（16:14 才 commit 的 8 个文件）经 Vite HMR 热更新生效到运行时，但构建期注入的 `gameBuild` 停留在启动时刻的 `5f77ecc`，且因启动时工作区存在 UX-3 未提交改动，`dirty` 置 true。

**置信度**：高。`hints` 字段存在性 + `cb4d22d` 提交时刻 < 导出时刻 + 协议 §4.2 快照语义三者互洽。唯一无法从遥测直接确证的是 dev server 的精确启动时刻，但可由 `gameBuild = 5f77ecc` 反推出启动时 HEAD 即 `5f77ecc`（若在其后任一 docs commit 之后重启，指纹应显示该中间 commit）。

### 4.3 严重度分级 —— Major（不阻断本轮，但属 B3 变体）

**定性**：数据完整性缺陷——「版本可追溯性」失效，`gameBuild` 字段不再能精确映射到代码状态。这是 B3（构建指纹）教训的**变体**：不是硬编码伪造值（B3 原缺陷），而是「构建期一次性注入 + 长运行 dev server」导致的**指纹过期/滞后**。

**为何是 Major 而非 Critical / Blocker**：

- 失真属「滞后」而非「造假」：`5f77ecc` 是试玩前曾经的真实 HEAD，非伪造值；
- 本次失真可被**内部证据自证纠正**（hints 字段存在性反证代码含 UX-3），未造成实质误判；
- UX-3 是纯 UI 层提示（RULES 零改动、simulation.js 零改动），不影响任何模拟数值。

**为何不是 Minor**：`gameBuild` 是规则 0 数据有效性的基础字段，若 naive 地只信 `gameBuild=5f77ecc`，会导出**方向相反的结论**——把「hints: [] 零触发」误读为「代码根本未实现提示功能，hints 字段无意义」，从而彻底推翻 R1 验证。只有 QA 交叉验证后才可消除误导。基础字段失真若不纠正，会系统性污染后续所有遥测的版本判断。

### 4.4 对验收数据的实际影响（区分两类数据）

| 数据类别 | 是否受失真影响 | 结论 |
|---|---|---|
| **节奏数据**（milestones / samples / prosperity / chainBreaks / scarcity / finalSnapshot） | **否** | 完全可信。UX-3 纯 UI 层、RULES 零改动、simulation.js 零改动；这些字段在 5f77ecc 时代已存在且 schema 一致，运行时数值正确性不受提示功能有无的影响。 |
| **提示遥测**（hints） | **是（需交叉验证）** | `hints: []` 的「零触发」结论**成立但依赖交叉验证**：前提是「代码含提示功能且正常运行」，该前提靠 `hints` 字段存在性（cb4d22d 新增）+ 时间线反证成立。若不纠正 gameBuild 误导，此结论会被推翻。 |

### 4.5 处置建议

1. **本轮数据标注**：节奏数据正常采信；hints 零触发结论采信，但在报告与后续引用处标注「gameBuild 指纹滞后，经 hints 字段存在性 + 提交时刻反证修正」。
2. **流程修复（短期，强制）**：试玩 SOP 增加硬前置——**每次试玩开始前重启 `npm run dev`，并在 HUD 面板核对「构建号」= 目标 commit**（本轮目标应为 `cb4d22d`，而非 `5f77ecc-dirty`）。未核对不采数据。
3. **治本（可选，建议纳入工程 backlog）**：将 `gameBuild` 从「构建期一次性注入」改为「导出 JSON 时实时读 git」或在导出时校验「当前运行 HEAD 是否等于注入指纹」，不一致则在 JSON 加 `gameBuildStale: true` 告警字段——使失真可被机读识别而非依赖人工交叉验证。

## 5. A4 口径核对 —— 未闭环，且存在假阳性风险

### 5.1 为何这两局不能计入 A4 分母

A4 判据（07 草案 §4，C-1 口径钉死）：

> **2 位不同新玩家 × 各自首局**（C-1：P2-G2 无提示已 89 tick ≤100，同玩家次局的学习效应会制造假阳性，故钉死首局口径）

本轮数据三处不符：

| A4 要求 | 本轮实际 | 判定 |
|---|---|---|
| 新玩家（novice） | 熟练玩家（主理人确认） | ❌ 画像不符 |
| 2 位**不同**玩家 | 1 位玩家 | ❌ 玩家数不符 |
| **各自首局** | 连玩 2 局（第 2 局非首局） | ❌ 首局口径不符 |

**结论：A4 分母为 0/2，主判据仍未闭环。** 这两局对 A4 的「新手徘徊段 ≤100 tick」与「提示 tick → 首个食肆 tick 跟随时延」两个子判据均无贡献（熟练玩家零触发，跟随时延无从测量）。

### 5.2 假阳性风险（须重点提示）

- **熟练玩家徘徊段实测 104 / 98 tick**——已大幅高于 07 草案引用的熟练参照 57~64 tick，且**贴近 A4 验收线 ≤100**；第 2 局 98 tick 甚至已落入 100 线内。
- 这意味着：**若仅以「徘徊段 ≤100 tick」作为 A4 通过判据，熟练玩家也能自然达标**（第 2 局已达标），A4 将失去对「提示是否真正生效」的判别力——这正是 C-1 口径修订要防的假阳性，本轮数据反而**用熟练玩家的 98 tick 实证印证了 C-1 的必要性**。
- 附加提示：07 草案「熟练参照 57~64」与本轮实测 98~104 存在明显落差，说明**熟练玩家徘徊段方差比预想大**（或本玩家当日状态/路线非最优），后续引用熟练参照时不宜当作固定常数。

**A4 通过的必要充分条件（须同时满足，缺一不可）**：

1. 2 位不同新玩家 × 各自首局（C-1 口径）；
2. 徘徊段 ≤100 tick；
3. **遥测 `hints` 能读出「提示 tick → 首个食肆 tick」的跟随时延**（证明是提示生效而非玩家本能，排除「无提示也达标」的假阳性）。

### 5.3 A5 无提示疲劳（附注）

两局 `hints: []`，单局 0 次 ≤ 3 表面达标，但这是**零触发**而非「疲劳控制生效」——A5 的验证需要「有触发」的局来证明「每条至多一次、关闭后不复发」。本轮对 A5 同样无效。
