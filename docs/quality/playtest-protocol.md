## 0. 一句话目的

用**真人试玩的到达时刻数据**回答一个问题：**当前节奏相对目标（D1′ 切片口径：Lv2 2~3 分钟 / Lv3 2~5.3 分钟 / Lv4 5~8 分钟，见 §5.1 判定带切换记录）偏离是否出带？** 出带 → 只动阈值杠杆（具体数值由设计侧从现行阈值 60/145 起重新标定；v1.2 预置的 50→60 / 100→120 为 pre-O6′ 历史口径，见规则 4）；未出带 → 不动。

**v1.1 核心原则**：玩家只负责「玩」，采集、计时、记录全部由游戏内自动采集模块在背后完成。玩家唯一要做的是通关后在面板上点两下（可选）并导出文件。

## 1. 采集指标定义（精确到可执行）

### 1.1 必采指标（自动采集，缺任一项该局数据作废）

| # | 指标 | 定义 | 采集方式 | 记录格式 |
|---|---|---|---|---|
| M1 | Lv2 到达时刻 | 繁荣度首次 ≥ 20 的游戏内 tick | **自动**（升级事件精确记录） | tick 数（整数） |
| M2 | Lv3 到达时刻 | 繁荣度首次 ≥ **60**（v1.3，O6′）的游戏内 tick | **自动** | 同上 |
| M3 | Lv4 到达时刻（通关） | 繁荣度首次 ≥ **145**（v1.3，O6′）的游戏内 tick | **自动** | 同上 |

> **v1.3 口径说明**：M1~M3 阈值与 `RULES.unlockThresholds`（现 20/60/145）同源——采集模块从配置派生，今后调阈值无需改本表，但仍须在版本变更记录里留痕。

**为什么记 tick 而不是分钟**：1 tick = 1 秒（`rules.tickMs: 1000`），tick 是节奏的物理量，不受 2× 加速、暂停、卡顿污染；分钟只是 tick 的展示换算（tick ÷ 60）。判定规则（第 5 章）全部以 tick 为准。

### 1.2 建议采集指标

| # | 指标 | 定义 | 采集方式 |
|---|---|---|---|
| M4 | 各阶段主要瓶颈感知 | Lv1→2 / Lv2→3 / Lv3→4 三段各是 缺木 / 缺钱 / 缺人（劳力）/ 缺食 / 无瓶颈 | **分析期从 samples / chainBreaks 客观推断**（玩家不再升级瞬间口头报告，推断方法见 3.2） |
| M5 | 首次断链发生时刻与类型 | 首次出现红色（缺料）/ 黄色（缺人）警示的 tick 与建筑类型 | **自动**（每建筑实例首次断链的 tick + 建筑类型 + 缺料/缺人） |
| M6 | 通关终局数据 | 到达 Lv4 瞬间的全量快照 | **自动**（通关瞬间 finalSnapshot） |
| M7 | 主观节奏评价 | 整体太快 / 适中 / 太慢 | **通关面板一键选择**（可不选） |
| M8 | 2× 使用情况 | 本局是否用过 2×、变速时刻 | **自动**（speedChanges + usedFastForward） |
| M9 | 空转帧占比（v1.3 新增，D-N2-4） | 无任何缺料/缺人约束的帧占比 = 1 − \|scarcity.materialTicks ∪ scarcity.laborTicks\| ÷ 总 tick 数 | **自动**（逐帧稀缺标记；samples 另带 30 tick 窗口计数 scarcityMaterial/scarcityLabor） |

> **M9 判定口径（D-N2-4 拍板）**：参考线 **< 40%** 是**无实测锚点的探索目标**（现网实测最低为小城模式 67.3%），**不作硬 Gate**；高占比与玩家水平正相关（抬阈值惩罚的恰是玩得好的人），终判以真人试玩体验为主。

> **M9/M9′ 新手口径注记（v1.4，沿 `playtest-judgment-20261018-round3.md` §5.2）**：新手 M9′ 呈双峰——救火型 44.1~52.0%（P2）、平稳型 95.7~98.2%（P3），对照熟练玩家 80.7% / bot 82.3%。**M9′ 在新手群体无区分能力**（其本质是稀缺压力的反向计），判定意义仅限熟练玩家口径（与 D-N2-9「只认 V2 自然路线」同旨）。另：M9′ 不区分「无事可做」与「玩家未行动」（如开局静默观察帧亦计入空转），引用时须注明。

### 1.3 M6 终局快照字段（自动采集，通关瞬间全量）

铜钱余额、市税收入、商业收入、木材 / 粮（含上限）/ 食（含上限）/ 器、户数 / 住房容量 / 劳力占用、繁荣度数值、建筑总数及构成。字段以 T-P6-02 实现的 finalSnapshot 为准。

## 2. 试玩协议（控制变量）

### 2.1 试玩前准备（每局必做）

1. **环境**：`cd D:/code/life && npm run dev` → 打开 `http://localhost:5173`，桌面 Chrome/Edge，窗口 ≥ 1280×720。
2. **清档开新局（按钮法）**：点击 HUD 新增的**「重开新局」**按钮（清档 + 开新局，替代 v1.0 的 console removeItem）。
3. **确认开局状态**：Lv1、繁荣 0.0、铜钱 240、木材 60、粮 20、食 20、户数 0/0。任何一项不符 → 再点一次「重开新局」。开局校验是玩家唯一的"操作负担"，约 5 秒。
4. 若面板未自动弹出或被误关，随时点 HUD 的**「试玩数据」**按钮可重新打开数据面板。

### 2.2 试玩环境与操作约束

| 项 | 约束 | 理由 |
|---|---|---|
| 速度档 | **第 1 局全程 1×，禁用 2×**；第 2 局起允许自由使用 2× | 2× 会把墙钟压半但 tick 不变；首局禁 2× 保证「普通玩家」画像数据纯净。**这是行为约束，不是采集负担**——自动采集不受影响 |
| 暂停 | 随意（自动采集不受暂停影响，tick 不推进即无数据） | 玩家自由 |
| 切标签页 | 尽量避免（引擎对后台 dt 钳制 250ms，长时间挂后台 tick 会变慢，影响真实体验） | 保证 tick 与真实秒的 1:1 关系 |
| 存档 | 不使用手动保存/读档；一局打完即结束，不开第二局续打 | 单局完整曲线才可比 |
| 指导 | **第 1 局前可读 README/操作说明；局中不查攻略、不问旁人** | 保留真实探索成本 |
| 中断 | 一局尽量一次打完（约 10~25 分钟）；被迫中断超过 5 分钟的局标记 `interrupted: true`（导出前在面板备注栏注明），数据仍收但单独归类 | 中断会改变心流状态，影响 M7 可信度 |

### 2.3 玩家画像自评（通关面板选择，可不选）

| 画像 | 判定标准（自评勾选） |
|---|---|
| 熟练 | 玩过 ≥2 款城建/经营模拟（如《宋上繁华》《模拟城市》《异星工厂》《纪元》等），且累计 ≥20 小时 |
| 普通 | 玩过 1 款同类游戏，或玩过但 <20 小时 |
| 新手 | 从未玩过城建/经营模拟类 |

> 判定基准（第 5 章）以**普通玩家**为目标口径；熟练/新手数据用于圈定区间上下界，不直接驱动调参。画像在通关面板选择（可留空，留空的局在分析期按 2.3 标准由组织者访谈补判，或标 unknown 不进判定组）。

### 2.4 样本量与局数（lean 档）

- **起步配置：单人 × 2~3 局**（第 1 局禁 2×，第 2~3 局自由）。
- 单人多局的意义：第 1 局代表「首见探索成本」，第 2 局起代表「已懂规则后的执行节奏」——两者都是设计目标（普通玩家 2~3/13/21）的组成部分。
- **升级触发条件**（满足其一即建议加采，交主理人拍板）：
  - 单人 3 局的 Lv4 到达时刻极差 > 30%（说明局内方差大，2~3 局不足以定位）；
  - 三局全部落在「偏离 > 30%」区间（将触发调参，调参决策值得更多证据）；
  - 出现任何一局卡死 > 5 分钟无进展（疑似新死锁/体验断崖，属 Bug 线索而非节奏问题）。
- lean 档明确接受：**单人数据不用于最终签字，只用于「是否偏离 > 30%」的方向判定**（风险见第 7 章）。

### 2.5 玩家操作速查卡（三步，可单独复制给试玩者）

```
1. 开局：点 HUD「重开新局」→ 确认繁荣 0.0 / 钱 240 / 木 60 / 粮 20 / 食 20 / 户 0
2. 正常游玩到通关（Lv4 toast）——全程零记录零操作，想暂停就暂停
   （第 1 局全程用 1×，别点 2×；尽量别切走标签页）
3. 通关自动弹出「试玩数据」面板：
   → 选画像（熟练/普通/新手，可不选）+ 节奏评价（太快/适中/太慢，可不选）
   → 有想说的写进备注框
   → 点「导出 JSON」→ 把下载的文件发回工作室
```

## 3. 自动采集说明（T-P6-02 实现的数据契约）

> 本章描述游戏内自动采集模块**采什么、精度多少**。玩家无感知；以下内容供分析期解读数据与工程验收共用。

### 3.1 采集内容与精度

| 数据 | 内容 | 精度 |
|---|---|---|
| milestones | Lv2/Lv3/Lv4 到达的 tick | **精确 tick**（升级事件当 tick 记录，无采样误差） |
| chainBreaks | 每建筑实例**首次**断链的 tick + 建筑类型 + 缺料（红）/ 缺人（黄） | 事件级精确（每实例只记首次，见 3.3 局限） |
| scarcity（v1.3 新增） | **逐帧**缺料/缺人标记（materialTicks/laborTicks 全量 tick 号）+ samples 窗口计数 | 帧级精确（每 tick 判定），M9 空转帧占比的数据源 |
| samples | 每 30 tick 一帧快照：资源 / 人口 / 繁荣度（+ 窗口稀缺帧计数） | 采样间隔 30 tick（0.5 分钟），两帧之间的瞬时波动不可见 |
| finalSnapshot | 通关（Lv4）瞬间的全量状态 | 精确（事件触发） |
| speedChanges | 变速时刻（含暂停/1×/2× 切换的 tick 与目标档位） | 事件级精确 |
| usedFastForward | 本局是否用过 2× | 布尔，由 speedChanges 派生 |

### 3.2 M4 瓶颈感知的推断方法（分析期，非玩家报告）

从 samples / chainBreaks 客观推断各阶段瓶颈，规则如下（分析期执行，写进判定报告）：

- **缺木**：samples 中 wood 长期贴 0 且林场数量少/未建 → 木瓶颈；
- **缺钱**：money 长期低位（< 下一目标建筑造价）且无断链警示 → 钱瓶颈；
- **缺人**：chainBreaks 中黄色（缺人）事件密集出现 → 劳力瓶颈；
- **缺食**：food 降至安全线 10 附近或以下、户数停止增长/迁出 → 食瓶颈；
- **无瓶颈**：资源曲线平稳上升、无 chainBreaks → 无。
- 每阶段（Lv1→2 / Lv2→3 / Lv3→4）按该段 tick 区间内的 samples + chainBreaks 归类，取主导信号。

### 3.3 自动采集的已知局限（分析期须知情）

1. **chainBreaks 只记每实例首次**：同一建筑反复断链/恢复只有第一次；「持续性瓶颈」需结合 samples 中该建筑类型的产出停滞推断。
2. **samples 30 tick 间隔**：两帧之间的瞬时断链（发生又恢复）不可见；对节奏判定（M1~M3 事件级精确）无影响，对 M4 推断是软限制。
3. **M4 是推断不是感知**：v1.0 的玩家主观瓶颈报告已删除，v1.1 的 M4 是「客观发生了什么」而非「玩家感觉缺什么」——两者可能背离（玩家没意识到的瓶颈不算他的体验痛点）。解读判定报告时须区分这两个口径。
4. **finalSnapshot 与 samples 时间基准不同（v1.4 新增，沿第 4 轮判定注记）**：finalSnapshot 冻结于 **Lv4 达成瞬间**；samples 采集延续至玩家**导出时刻**（通关后继续游玩的时段也会进入 samples）。引用终局状态以 finalSnapshot 为准，samples 尾段不代表通关态。

## 4. 数据回传格式（结构化，供 design-strategist 分析）

### 4.1 回传物

玩家通关后从面板点「导出 JSON」，得到 `playtest-session-<时间戳>.json`，直接发回工作室（建议落 `production/playtests/`，或经主理人转交 design-strategist）。

### 4.2 JSON schema（playtest-protocol@1.3）

```json
{
  "protocol": "playtest-protocol@1.3",
  "gameBuild": "<commit hash>[-dirty]",  // 构建期由 vite.config.js 从 git 注入：git rev-parse --short HEAD
                                         // 工作区有未提交改动时追加 -dirty；git 不可用时为 "unknown"
  "gameBuildDirty": true,                // 可机读的 dirty 标记（true = 该 build 号不对应任何干净 commit）
                                         // 与 gameBuild 后缀同源，供分析脚本直接判定，无需解析字符串
  "exportedAt": "2026-10-XXThh:mm:ss",
  "playerProfile": "normal",        // skilled | normal | novice | null（面板未选）
  "paceVerdict": "too-fast",        // too-fast | ok | too-slow | null（面板未选）
  "notes": "",                       // 面板备注文本框
  "milestones": {                   // 精确 tick；null=未发生；阈值口径 = RULES.unlockThresholds（现 20/60/145）
    "lv2": 300, "lv3": 780, "lv4": 1260
  },
  "chainBreaks": [                  // 每建筑实例首次断链
```

> **`gameBuild` 读法（v1.2 补充，B3 修复）**：该字段由 `vite.config.js` 在构建期用 `git rev-parse --short HEAD` + `git status --porcelain` 注入（dev 与 build 均生效），不再是硬编码常量。

## 5. 判定规则预置（把设计案 8.6 纪律转写为机械规则）

### 5.0 前置换算

tick → 分钟：**1× 全程时 分钟 = tick / 60**；用过 2× 的局，tick 仍是游戏内时间，直接 tick/60 得「游戏内分钟」——**判定一律用游戏内分钟**（与 bot 的 8.4 分钟同口径，bot tick 504 → 504/60 = 8.4）。

### 5.1 目标值对照表（普通玩家口径，来自设计案 5.4/8.6）

| 里程碑 | 目标（D1′ 切片口径，2026-10-18 切换） | 目标 tick（1× 等效） | 判定方式 | bot 实测参照（v1.3 口径） |
|---|---|---|---|---|
| Lv2 | 2~3 分钟（v1.2 下修，设计决策 D2 2026-10-17） | 120~180 | [84, 234]（±30%）；**D4 教学检查点，不参判仅记录** | tick 12 ≈ 0.2 分钟 |
| Lv3 | **2~5.3 分钟（D1′ 钉带）** | **120~320** | **带内 PASS；<120 偏快；>320 偏慢**（锚点 = 新玩家 4 局 128~310，中位 265.5） | tick 355 ≈ 5.9 分钟 |
| Lv4 | **5~8 分钟（D1′ 双轨制竖切片目标）** | **300~480** | **带内 PASS；<300 偏快；>480 偏慢**（锚点 = 新玩家 4 局 311~488，中位 412） | tick 605 ≈ 10.1 分钟 |

> **判定带切换记录（2026-10-18，D1′ 落实）**：Lv3/Lv4 原 780/1260（±30%）为「维持 1260」时代口径，经 D1′ 双轨制拍板降级为**完整版愿景目标挂起**（与 P2 内容量绑定，内容落地后重新标定）；现行切片判定带由 B2 闭环后的新玩家 4 局数据钉死（判定报告 `playtest-judgment-20261018-round3.md` §4）。
> 熟练玩家参照（**D1′ 后不设时长下限，仅观测**）：2 / 7 / 13 分钟为 v0.3 推演历史口径。
> **bot 参照口径（v1.3 升版）**：上表为 **2026-10-18 O6′ 基线、现行验收 bot**（12/355/605，V1 注入铜钱 211）。v1.2 及之前的 11/286/504 是 pre-D0 旧 bot 口径（高估真实通关下限 3.71 倍），仅作历史归档。**纪律重申（HANDOVER §5/B4）**：bot 是贪心启发式、非「最优玩家下限」，bot tick 只用于可达性验收参照，**不得用作节奏目标映射**；真人下限硬事实为 L\*_human=139（真人标定，不受 bot 更换影响）。

### 5.2 机械判定规则（按序执行，规则 0 优先于一切）

- **规则 0（数据有效性）**：进入判定的局必须满足——① **自动采集数据**（`timingMethod` 固定值 `auto`，即 milestones 由游戏内模块事件级记录）；② 通关（有 M3/lv4）；③ 开局校验通过（240/60/20/20/0）。**开局校验口径（v1.2 修正）**：samples 首帧并非 tick 0 快照——collect 在 tick 递增后调用，实际首帧在 tick 30（首帧 tick 以实现为准）；核验方式为「**首帧（tick 30）快照 + 开局至首帧的开销推算**」**人工核验**，即以实际首帧快照为准、按已发生的建造开销回推初始态是否符合 240/60/20/20/0。不满足的局只入附录，不参与判定。
- **规则 1（画像分桶）**：按 2.3 画像分组；**普通玩家组为判定组**。普通组为空时（如试玩者只有熟练玩家或面板未选画像且无法补判）→ 触发「数据不足以判定」，见规则 5。
- **规则 2（代表值）**：判定组内取各里程碑 tick 的**中位数**为代表值（不用均值，抗单局离群）。
- **规则 3（偏离判定，v1.2 修正符号歧义）**：对 Lv2/Lv3/Lv4 三个里程碑分别比较实测中位数与目标。**方向定义：实测比目标快 = 偏快；实测比目标慢 = 偏慢。**（等价公式 `偏离度 = (实测中位数 − 目标) / 目标`：负值 = 偏快，正值 = 偏慢——注意偏离度为**负**才是偏快，避免旧版符号歧义。）
  - **偏快判定：实测中位数 < 目标 × 0.7**（即比目标快超 30%，偏离度 < −30%）；**偏慢判定：实测中位数 > 目标 × 1.3**（偏离度 > +30%）。Lv2 为区间目标（120~180 tick）时：偏快对**区间下沿**取 −30%（实测 < 84 tick），偏慢对**区间上沿**取 +30%（实测 > 234 tick）。
  - **整体判定**：三个里程碑中**至少 2 个**满足偏快判定 → 判「整体偏快，触发调参」；
  - 至少 2 个满足偏慢判定 → 判「整体偏慢」（当前无此迹象，出现时**不自动套杠杆**，回传设计侧另议——减速杠杆清单只覆盖偏快方向）；
  - 其余情况 → 判「在容差内，不动数值」。
  - 单里程碑满足偏快/偏慢判定但不满足「至少 2 个」→ 判「局部偏快，观察」，附数据回传再议，不动杠杆。
- **规则 4（杠杆选择，仅在判「整体偏快」时执行）**：**只动一个杠杆，首选提高解锁阈值**——
  - **【v1.3 口径警示】本规则原预置数值（优先级 ①：Lv3 50→60 或 Lv4 100→120）为 pre-O6′ 历史口径**：50→60 已随 O6′ 落地（现阈值 20/60/145 + 恒计分封顶 26），100→120 已被 P-1′ 双 Gate 探针实测否决（Lv4 阈值存在验收 bot 可达性硬边界，且封顶后「贴线过」余量极小）。**后续任何杠杆的具体数值必须由设计侧从现行基线重新标定并过双 Gate 探针（V2 自然通关 + V1 注入铜钱），本协议不再预置数字**；
  - 选哪个档位的参考逻辑不变：若偏快集中在 Lv2→Lv3 段（M2 偏离最大）→ 动 Lv3；若集中在 Lv3→Lv4 段（M3 偏离最大）→ 动 Lv4；
  - 优先级 ②（迁入间隔 5→8）与 ③（降食肆产出）**维持禁用**（设计案 8.6；迁入 5→8 已经逐帧诊断证伪机制性收益，见 HANDOVER §6.1）；
  - 任何杠杆动后必须重跑 `npx vitest run --config vitest.verification.config.js` 确认 bot 仍自然通关 Lv4（HANDOVER 纪律 1）。
- **规则 5（数据不足）**：普通组有效局 < 2，或画像无法归组 → 判「数据不足以判定」，建议加采（见 2.4 升级触发条件），本轮不动数值。

## 7. 风险与局限声明（测试负责人提示）

1. **单人 2~3 局的样本局限（最大风险）**：单人数据反映的是「这个人」的节奏，不是玩家分布。本协议的判定只做**方向性结论**（偏快/不偏快），不做幅度结论（偏快多少分钟）。若据此动阈值，动后需再采一轮验证（预期：阈值 +20% 大约把对应段拉长 15~25%，非精确线性）。
2. **画像自评偏差**：试玩者容易高估自己（勾「普通」实为新手）。缓解：用数据反推画像修正。**v1.4 修订**：旧经验法则「新手首局 Lv2 通常显著慢于 5 分钟」已被证伪——新玩家 4 局 Lv2 = 47/39/125/95 tick，全部 <150 tick（恒计分建筑即买即达，Lv2 快慢不区分新手与熟练）；**现行新手鉴别信号为 Lv2→Lv3 徘徊段时长**（新手 169~220 tick vs 熟练 57~64 tick，依据 `playtest-judgment-20261018-round3.md` §3）。**v1.1 新增**：面板画像可不选，未选的局须访谈补判或标 unknown 不进判定组，防止"懒得选"污染分桶。
3. **学习效应**：第 2、3 局系统性快于第 1 局（已懂规则）。这不是噪声，是设计目标的一部分（普通玩家含探索成本），但**不要拿第 3 局数据单独代表「普通玩家」**——判定用中位数正是为此。
4. **2× 污染主观指标**：tick 不受 2× 影响（判定安全），但 M7 节奏评价会被 2× 压缩（等待感消失→「太快」评价失真）。故第 1 局禁 2×，M7 优先取自 1× 局。
5. **M4 从数据推断的口径局限**：v1.1 的 M4 是客观瓶颈（数据推断），不是玩家主观感知——玩家没意识到的瓶颈不会出现在任何字段里。判定报告须标注「M4 为客观口径」，体验侧结论（玩家觉得卡在哪）需另行访谈，两者背离时以访谈为准。
6. **自动采集模块本身需工程单测 + 冒烟验证**：本协议全部数据可信度建立在 T-P6-02 模块正确性之上。工程侧交付时须含：① 单测（milestones tick 精确性、chainBreaks 首次判定、samples 间隔、finalSnapshot 完整性、speedChanges 记录）；② 冒烟（真实浏览器跑一局 bot/人工短局，核对导出 JSON 与 HUD 读数一致）。**模块未过验证前，本协议数据不进入判定**。
7. **本协议不采集的**：UI 可用性细节、崩溃/报错（如有，写进面板备注栏，走 Bug 流程另开报告）；这些属后续 QA 任务范围。
8. **判定纪律重申**：本判定为**建议性门控（advisory）**——quality-lead 给出 PASS/CONCERNS/FAIL 式结论与杠杆建议，最终是否动阈值由用户拍板；且动后必须过独立验收推演（`tests/verification/`），未过不算完成。
